# Specification workflow

PersonaKit will use [OpenSpec](https://github.com/Fission-AI/OpenSpec) with [spec-ctx](https://github.com/sonqh/spec-ctx). The repository does not yet contain an initialized OpenSpec project.

## Bootstrap on a development machine

Use Node.js 22 or newer. Initialize OpenSpec before spec-ctx.

```bash
npx -y @fission-ai/openspec@latest init --tools claude --no-animation
npx -y spec-ctx@0.4.1 init --all
npx -y spec-ctx@0.4.1 status
npx -y spec-ctx@0.4.1 gate --strict
```

After `init`, register the capability codes. `specctx id new REQ PER` exits with code 2 unless the code is in `[ids] caps`. Add this line under `[ids]` in `spec-ctx.toml`:

```toml
caps = ["PER", "VIS", "ONB", "AIP", "CV", "BUG", "ARC"]
```

Then rebuild the index:

```bash
npx -y spec-ctx@0.4.1 build
```

Review the generated configuration. Commit the OpenSpec files, templates, and agent skill. The bootstrap commands are instructions. We have not executed them in this design change.

## Requirement IDs

Use spec-ctx to allocate IDs after initialization. Register these capability codes during bootstrap:

| Code | Capability |
| --- | --- |
| PER | Persona records |
| VIS | Visibility and export |
| ONB | Onboarding and review |
| AIP | AI context packs |
| CV | CV projections |
| BUG | Bug reporting and diagnostics |
| ARC | Archive export and restore |

For example, request a new requirement ID with `specctx id new REQ PER`. Do not invent or reuse an ID in a change. Use the ID generated by the installed tool.

## Change workflow

1. Start a small OpenSpec change.
2. Write its proposal, design, requirement deltas, and tasks.
3. Allocate stable requirement and scenario IDs with spec-ctx.
4. Link each task to its requirements.
5. Add a `Verify:` command to each task.
6. Run `specctx task next` and `specctx task start <task>`.
7. Implement the change and add tagged code and tests.
8. Run `specctx task done <task>` only after verification passes.
9. Run `specctx check --strict` and `specctx gate --strict` before a pull request.
10. Write the handoff and archive when the change is complete.

A failing Verify command must leave the task open. Do not mark tasks complete by editing their checkboxes.

Commit the task evidence in `.ctx/evidence/` because `specctx check --strict` needs it. The `.gitignore` file excludes the `*.fail-*.json` files because they are logs for each attempt.

## Agent guidance

Read only the context needed for the current task. The generated `specctx-run` skill provides the task loop. Do not duplicate that loop in custom scripts before a specific gap is found.

Use [ste-humanize](https://github.com/sonqh/ste-humanize-skill) for README files, design notes, issue text, and PR descriptions. Use its Human mode for prose and Strict mode for agent instructions and errors.

```bash
npx skills add sonqh/ste-humanize-skill
```

The skill must be installed in the agent's actual environment. A link to the repository alone does not load the skill.

## Separation of responsibilities

spec-ctx tracks product requirements, code, tests, and verification evidence. PersonaKit tracks user-owned facts and the sources of those facts. A spec-ctx ID must never be used as a personal record ID.

A bug report can reference an existing requirement ID. It must not silently rewrite that requirement. Use a new OpenSpec change when the expected behavior needs to change.
